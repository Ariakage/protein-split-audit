# ProteinSplitAudit v0.3.0 Classical Baseline Protocol

## Status

This document defines the v0.3.0 classical sequence-baseline protocol. It is validation-only. The
machine-readable freeze attestation will be written to
`docs/attestations/v0.3.0-protocol-freeze.yaml` after the implementation, deterministic replay,
clean generation commit, and permanent GitHub approval comment are available.

The attestation, not this document alone, records the approved protocol hash and generation
identity. Until that attestation exists and verifies, results are development outputs and are not
release-approved.

## Research boundary

ProteinSplitAudit v0.3.0 asks an engineering question: can five simple sequence baselines be trained
and evaluated consistently on the frozen v0.2.0 cohort and split definitions without allowing
Validation or Test information into model fitting?

This release does not make a final scientific claim about homology leakage or model
generalization. It does not add ESM-2, deep learning, automatic hyperparameter search, repeated
seeds, or a new cohort or split. It does not run the real Test split.

The version sequence is intentional:

- v0.2.0 freezes the cohort, similarity groups, and split assignments;
- v0.3.0 evaluates classical baselines on Validation;
- v0.4.0 evaluates planned ESM-2 methods on Validation;
- v0.5.0 may open Test for the first time after a separate Test-freeze attestation.

## Baseline matrix

The formal Validation matrix contains exactly five baselines across four splits, for 20 cells:

1. Majority Class;
2. Sequence Length plus Logistic Regression;
3. Amino-acid Composition plus Logistic Regression;
4. fixed 3-mer relative frequency plus Logistic Regression;
5. Nearest Training Homolog.

The formal runtime seed is 42. v0.3.0 has one formal seed and performs no hyperparameter search.

## Feature definitions

### Sequence Length

The raw feature is the sequence length and nothing else. A `StandardScaler` is fitted on Train and
then used to transform Validation. Sequence length is recomputed from the verified sequence and
must equal the frozen cohort value.

### Amino-acid composition

The alphabet and feature order are fixed:

```text
ACDEFGHIKLMNPQRSTVWY
```

For amino acid `a` in a sequence of length `L`:

```text
AAC[a] = count(a) / L
```

The result is a 20-column `float64` matrix. Every row sums to 1 within an absolute tolerance of
`1e-12`. A `StandardScaler` is fitted on Train and then used to transform Validation.

### Fixed 3-mer relative frequency

The 3-mer protocol is:

```yaml
kmer3:
  k: 3
  alphabet: ACDEFGHIKLMNPQRSTVWY
  vocabulary: fixed_complete
  feature_count: 8000
  normalization: relative_frequency
  sparse_format: csr
  dtype: float64
  preprocessing:
    scaler: none
```

The vocabulary is the complete ordered Cartesian product of the alphabet, from `AAA`, `AAC`,
`AAD`, through `YYY`. It is never learned from the cohort or any split.

For a sequence of length `L`, feature `j` is:

```text
x[j] = count(kmer[j]) / (L - 3 + 1)
```

The matrix is SciPy CSR with sorted indices and `float64` data. It is not converted to a dense
pandas table. No scaler, TF-IDF, feature selection, vocabulary pruning, hashing trick, or learned
normalization is applied. For every valid input sequence, the 3-mer values sum to 1 within floating-
point tolerance.

## Logistic Regression

Length, AAC, and 3-mer share one fixed classifier definition:

```yaml
type: logistic_regression
solver: lbfgs
penalty: l2
C: 1.0
class_weight: balanced
max_iter: 5000
tol: 0.0001
fit_intercept: true
random_state: 42
```

Class weights are derived from Train labels only. Length and AAC use their Train-fitted scalers;
3-mer enters the classifier directly as relative-frequency CSR. Any scikit-learn
`ConvergenceWarning` fails the run. Parameters must not be changed after seeing Validation or Test
results.

## Majority Class

The baseline counts Train labels only and predicts the most common label. If multiple labels tie,
it chooses the lexicographically smallest EC string. The selected label and Train counts are
recorded in the model manifest.

## Nearest Training Homolog

The approved search definition is:

```yaml
nearest_homolog:
  engine: mmseqs2
  search:
    minimum_coverage: 0.80
    coverage_mode: 0
    evalue_threshold: 0.001
    sensitivity: 7.5
    alignment_mode: 3
    threads: 8
  target_database: train_only
  no_hit:
    policy: training_majority_class
    record_explicitly: true
```

The target database contains Train sequences only. Validation sequences are queries only and are
never added to the target database. Formal runs use eight threads; unit tests use one thread or
mocked output, and CI performs no real full-data MMseqs2 search.

MMseqs2 output order is not trusted. Accepted hits are parsed and sorted by:

1. bitscore descending;
2. e-value ascending;
3. percent identity descending;
4. query coverage descending;
5. target coverage descending;
6. target accession ascending.

The first sorted hit supplies the predicted label. A query with no accepted Train hit uses the
Train-majority label and records `no_hit: true`. Reports keep fallback cases separate through:

- `no_hit_count`;
- `no_hit_rate`;
- `no_hit_correct_count`.

The e-value threshold is a project protocol choice, not a claim that it is the only valid MMseqs2
setting.

## Leakage controls

- Cohort membership and split assignment are inherited unchanged from v0.2.0.
- Feature, model, and evaluation code materializes Train and Validation records only.
- Opaque file hashing may read bytes to verify a frozen artifact, but Test sequence/label records
  are not parsed into feature, model, or evaluation objects.
- StandardScaler, class weights, majority label, Logistic Regression, and all learned statistics
  fit on Train only.
- The complete 3-mer vocabulary is fixed before reading any data.
- The Nearest Homolog target database contains Train only.
- Validation labels are joined only after predictions exist.
- Validation results cannot change the frozen v0.3.0 parameters without a new protocol identity
  and attestation.
- Test labels, sequences, features, predictions, and metrics are not generated in v0.3.0.

## Metrics

Primary metrics:

- Macro-F1;
- Balanced Accuracy, computed as macro recall over the frozen label order.

Secondary metrics:

- Accuracy;
- Macro Precision;
- Macro Recall;
- per-class precision, recall, F1, and support;
- fixed-order confusion matrix;
- prediction coverage;
- training time, prediction time, and sampled peak resident memory.

Nearest Homolog additionally reports hit coverage, no-hit aggregates, and the count, minimum,
median, mean, p90, p95, and maximum of nearest identity over accepted hits. Empty hit sets retain a
zero count and use `null` for distribution statistics.

Metric functions use the frozen label order explicitly and `zero_division=0`. Timing and memory are
run-specific provenance, not deterministic content identities.

## Validation and Test access

The allowed development and formal commands are validation-only:

```text
psaudit experiment run --config configs/experiment/v030-validation.yaml \
  --split <random|cluster70|cluster50|cluster30> \
  --baseline <baseline-name>

psaudit experiment matrix --config configs/experiment/v030-validation.yaml
```

v0.3.0 also implements a denial gate:

```text
psaudit experiment finalize-test --config configs/experiment/v030-test.yaml
```

The active attestation fixes:

```yaml
experiment:
  evaluation_split: validation
  real_test_access_authorized: false
```

The Test command must read this authorization before opening any real row-level split, cohort FASTA,
feature cache, model, or output directory. It exits nonzero with:

```text
ERROR: Real test access is not authorized by the active attestation.
```

A clean Git tree or confirmation flag cannot override the false authorization. Real Test access is
deferred to a separately approved v0.5.0 Test-freeze attestation.

## Provenance and attestation

Formal Validation runs record the package and library versions, MMseqs2 version and sanitized
command, fixed thread count, exit code, Git commit/dirty state, `uv.lock` hash, input/config hashes,
feature and model identities, prediction/metric hashes, and run-specific resource measurements.

The machine-readable attestation path is:

```text
docs/attestations/v0.3.0-protocol-freeze.yaml
```

It must contain:

- this protocol's SHA-256;
- the full clean generation commit;
- `git_dirty: false`;
- the `uv.lock` SHA-256 and Python 3.12 version;
- the cohort row-manifest SHA-256;
- all four split row-manifest SHA-256 values;
- the frozen Validation experiment identity;
- `real_test_access_authorized: false`;
- approver identity and actual approval UTC time;
- a permanent GitHub Issue or PR comment URL as `approval_reference`.

No placeholder hashes, dates, or approval URLs may be committed. Creating an Issue, PR, comment,
commit, tag, or Release requires separate maintainer authorization.

## Artifact policy

Feature caches, fitted models, prediction rows, nearest-neighbor rows, confusion matrices, logs,
raw/processed sequences, and complete run directories remain ignored and local.

After review, v0.3.0 publishes only:

```text
results/released/v0.3.0/
├── validation_summary.csv
├── validation_per_class.csv
├── feature_schema.json
├── environment_summary.json
├── protocol_attestation.yaml
└── README.md
```

No `test_summary.csv`, Test per-class metrics, Test confusion matrix, record-level prediction,
accession listing, raw sequence, model binary, private path, or secret is published.

## Known limitations

- The cohort is a five-class E. coli K-12 Pilot, not a representative sample of all reviewed
  bacterial enzymes.
- One seed and one fixed parameter set support pipeline validation, not a multi-seed main study.
- MMseqs2 results remain dependent on the recorded tool version and protocol settings.
- Majority, Length, AAC, 3-mer, and Nearest Homolog are intentionally simple baselines.
- Validation-only results cannot establish final generalization performance.
- The real Test split remains untouched until the separately approved v0.5.0 workflow.
